# SPEC-KIT — Frontend Developer Standards

- 버전: 3.0
- 대상: HTML5, CSS3, Modern Vanilla JavaScript(ES Modules)
- 목적: 바이브 코딩의 구현 일관성·접근성·유지보수성 확보
- 우선순위: 사용자 요구사항 > 프로젝트 기존 구조/디자인 시안 > 본 문서의 기본 규칙. 충돌 시 변경 전 보고한다.

## 1. AI 개발 작업 프로토콜
1. **분석**: 기존 파일 구조, DOM, CSS 선택자, 미디어쿼리, 자산 경로, 데이터 구조, 이벤트를 확인한다.
2. **계획**: 수정 대상 파일과 섹션, 재사용할 코드, 예상 영향 범위를 짧게 제시한다.
3. **구현**: 요청 범위만 최소 수정한다. 기존 클래스명·동작·콘텐츠를 임의로 변경하거나 전체 재작성하지 않는다.
4. **검증**: 콘솔, 링크/이미지 경로, 키보드, 반응형, 데이터 오류, 모션 설정을 점검한다.
5. **보고**: 수정 파일, 핵심 변경, 테스트 결과, 미검증 항목과 남은 이슈를 명시한다. 실행하지 않은 테스트를 통과했다고 주장하지 않는다.

## 2. 기술 스택과 아키텍처
- 기본은 시맨틱 HTML, CSS Custom Properties/BEM, Vanilla JS ES Modules다. 외부 라이브러리는 명시적 승인이나 명확한 필요가 있을 때만 도입한다.
- 파일 분리는 프로젝트 규모에 비례한다. 소규모 사이트에는 `index.html`, `css/style.css`, `js/app.js`, `images/`로 충분할 수 있다.
- 규모가 커지면 `css/{tokens,base,layout,components,responsive}.css`, `js/{components,utils,data,app}.js`로 분리한다.
- Store, EventBus, DI 컨테이너는 복수 컴포넌트의 공유 상태·복잡한 이벤트 흐름이 실제로 필요할 때만 사용한다.
- 프로젝트의 기존 디렉터리와 파일명 규칙을 우선한다.
- ES Modules는 로컬 파일 직접 열기가 아닌 개발 서버(HTTP) 환경에서 테스트한다.

## 3. HTML 및 접근성
- `header`, `nav`, `main`, `section`, `article`, `footer` 등 의미에 맞는 요소를 사용한다. `section`에는 가능한 한 접근 가능한 제목을 제공한다.
- 목록에는 기본 `ul/li` 의미를 활용하고 불필요한 `role=list/listitem`을 중복 선언하지 않는다.
- 단순 카테고리 필터는 일반 버튼 그룹(`aria-pressed` 등)을 우선한다. 실제 탭 인터페이스일 때만 `tablist/tab` 및 화살표 키 이동, 패널 관계를 완성한다.
- 모달은 가능하면 네이티브 `<dialog>`와 `showModal()`/`close()`를 사용한다. 열기 버튼으로 포커스를 되돌리고 Escape·닫기 버튼·배경 클릭 정책을 명확히 한다.
- 커스텀 모달을 쓴다면 `aria-modal`, 포커스 관리, 배경 비활성화, 스크롤 복원, 중첩 모달 처리까지 구현한다.
- 동적으로 주입되는 외부 데이터에 `innerHTML`을 직접 사용하지 않는다. `textContent`, `createElement` 등을 우선하고, 신뢰 가능한 정적 마크업만 제한적으로 허용한다.

## 4. CSS 및 반응형
- 디자이너 규약의 토큰과 브레이크포인트를 공유한다. 기본값은 Desktop First, `@media (max-width: 1024px)` 및 `@media (max-width: 390px)`다.
- 391~1024px 사이의 유동 축소를 보장하고, 콘텐츠가 깨지는 경우 근거를 제시해 추가 브레이크포인트를 설정한다.
- BEM을 권장하되 기존 프로젝트 명명법을 무리하게 바꾸지 않는다.
- `transition: all`과 깊은 선택자 의존을 피한다. 애니메이션은 `transform`·`opacity`를 우선하고 `prefers-reduced-motion`을 지원한다.
- 이미지·폰트·배너에는 적절한 크기 예약과 로딩 전략을 적용해 CLS를 줄인다.

## 5. JavaScript 구현
- 전역 네임스페이스 오염을 최소화하고 모듈 또는 함수로 책임을 구분한다.
- 반복 생성 목록은 필요에 따라 이벤트 위임을 사용한다. `event.target`이 Element가 아닐 수 있음을 고려한다.
- 등록한 이벤트·Observer·타이머는 컴포넌트 제거 시 정리한다. 단, 페이지 수명과 같은 리스너까지 불필요하게 해제하지 않는다.
- 상태 관리는 먼저 단순한 지역 상태를 사용한다. 공유 상태가 복잡해질 때만 Store를 도입한다.
- `Object.freeze()`는 얕은 동결이므로 중첩 객체 불변성을 보장한다고 가정하지 않는다.
- 선택적 체이닝은 값이 선택 사항일 때 사용하며, 필수 데이터 누락은 명확한 오류 처리와 사용자 안내를 제공한다.
- DOM 업데이트 시 `DocumentFragment`, 템플릿, 필요한 노드 변경 등 적절한 방법을 사용한다.

## 6. 데이터·자산·보안
- 실제 콘텐츠를 원본 사이트에서 수집했다면 출처, 수집일, 이용 허용 범위, 저작권·라이선스를 확인한다. 무단 재배포를 전제로 하지 않는다.
- JSON 데이터는 스키마/필수 필드/빈 값/중복 ID를 검증하고, 잘못된 레코드에 대한 안전한 대체 UI를 제공한다.
- 이미지 파일은 경로, 확장자, 대소문자, 404 여부를 확인한다. 외부 이미지 핫링크보다 사용 권한을 확인한 로컬 자산을 우선한다.
- 외부 URL은 허용 프로토콜을 검증하고, 사용자 제공 HTML은 무조건 신뢰하지 않는다.
- 비밀키·토큰·개인정보를 프론트엔드 코드나 공개 저장소에 포함하지 않는다.

## 7. 성능과 품질 목표
- 콘솔의 미처리 오류 0건을 목표로 하며, 경고는 원인과 영향에 따라 처리한다.
- Core Web Vitals 목표(75백분위 실사용 데이터 기준): LCP 2.5초 이하, INP 200ms 이하, CLS 0.1 이하.
- Lighthouse 점수는 테스트 환경과 콘텐츠에 따라 달라지므로 절대 보증하지 않는다. 프로젝트별 목표를 설정하고 측정 조건을 기록한다.
- 반응형 테스트: 320, 375, 390, 768, 1024, 1025, 1440px 이상.
- 키보드: Tab, Shift+Tab, Enter, Space, Escape 및 해당 위젯의 방향키 동작을 점검한다.
- 지원 브라우저와 기기 범위는 프로젝트 시작 시 합의한다.

## 8. 구현 완료 기준(Definition of Done)
- [ ] 요청한 기능과 시안이 구현되었다.
- [ ] 기존 기능·DOM·CSS가 의도치 않게 훼손되지 않았다.
- [ ] 브라우저 콘솔의 미처리 오류와 자산 404가 없다.
- [ ] 모바일 메뉴, 모달, 필터, 링크, 키보드 동작을 점검했다.
- [ ] 작은 화면에서 넘침·겹침·잘림을 점검했다.
- [ ] 외부 데이터 입력과 DOM 주입을 안전하게 처리했다.
- [ ] 실행한 테스트와 실행하지 못한 테스트를 구분해 보고했다.
